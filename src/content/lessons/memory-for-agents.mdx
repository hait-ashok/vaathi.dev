<p class="mono-label">Scene</p>

Imagine **Ash** — organising a small meetup, not an engineer. Yesterday Ash asked an assistant which room was free; it looked something up and said **Hall B**. This morning Ash opens a new chat and asks again: “Which room did we book?”

Silence. Not rude — **empty**. The model did not attend yesterday. Nothing was saved for today.

That gap is why agents need memory. Memory is **storage you control**, plus rules for when to save and when to reread — not a smarter brain. See also: [Glossary — Agent memory](/glossary#agent-memory).

## Why it matters for Ash

| If nothing is saved… | What Ash feels |
| --- | --- |
| Multi-step booking | Ash repeats the same lookup |
| “Keep answers short” | Tone resets every new chat |
| Hall B from a tool | The fact vanishes when the window fills or the tab closes |

Agents [loop](/learn/foundations/agentic-workflows). Loops only stay useful if useful facts **survive** the next turn.

## Three kinds (enough)

| Kind | Where it lives | For Ash |
| --- | --- | --- |
| **Short-term** | This chat’s message list | Hall B still on screen in *this* thread |
| **Session** | A short summary of the run | “We already booked Hall B” |
| **Long-term** | A store outside the model | Prefs, FAQ notes, saved facts next week |

Long-term often uses [embeddings](/learn/foundations/why-vectors-embeddings) to *find* notes — retrieval, not the model “learning” Ash’s meetup by magic.

## How you configure it (four knobs)

Before picking a vendor, write Ash’s answers:

1. **What** — full chat, a one-line summary, or facts only (`meetup_room=Hall B`)  
2. **Where** — only in the prompt, or a real store (file, DB, vector index)  
3. **When** — every turn, end of session, or only when Ash says “remember this”  
4. **Budget** — max messages / tokens / chunks, and who can delete  

Mental model: **read policy + write policy + store + size limit**.

## Market map (not a tour)

| Region | Job | Beginner cue | Examples |
| --- | --- | --- | --- |
| **Chat products** | Built-in chat / custom memory | Notice it; don’t bet an app on it | Consumer chat “memory”, project spaces |
| **Frameworks** | You wire history + stores in code | When you build | LangChain / LangGraph, LlamaIndex |
| **Session / KV stores** | Prefs + summaries | Simple long-term | Redis, DynamoDB, Postgres |
| **Vector / knowledge** | “Find relevant notes” | RAG-shaped memory | pgvector, OpenSearch, Bedrock Knowledge Bases |
| **Memory specialists** | Profiles / facts over time | Optional later | Mem0, Zep |

For Ash’s room name: **last N messages + one saved fact** beats a fancy memory product. Add vectors when the job is “search my notes,” not “remember Hall B.”

## Takeaway

**Memory = sticky notes you file and hand back to the model** — configured storage, not a feature the model invents.
